# Remis Agent / Copilot：产品意图契约

本文描述 Remis 面向普通用户的自然语言助手。当前实现和差距见
[Agent / Copilot 开发契约](developer/agent-copilot-contract.md)，用户说明见
[Remis 小助手](user-guides/remis-assistant.md)。

## 文档状态

- 功能：Remis Agent / Copilot
- 3.1.0 状态：内部／隐藏工程预览，普通打包用户不可用
- 下一版本目标：向普通用户开放
- 产品决定人：玲珑

- 相关愿景：[Issue #132](https://github.com/Drlinglong/Remis/issues/132)

## 一个入口，两种职责

Agent 和 Copilot 在实现职责上不同，但作为一整个产品交给用户：

- **Copilot** 负责回答“Remis 是干什么的”“这个模块怎么用”“下一步去哪”等问题，是进阶
  版新手教学；
- **Agent** 负责理解“我要汉化这个 Mod”“检查更新后挖新词、增量翻译并生成封面”等目标，
  把自然语言转成受治理的 Remis 工作流计划。

用户不需要切换模式。在同一个聊天框里，她既可以问“增量翻译是什么”，也可以说“我要
汉化这个 Mod”。

## 用户为什么需要它

Remis 功能完整，但普通用户未必理解模块关系、正确顺序和风险边界。助手需要同时降低两类
阻力：

1. 不知道某个功能做什么、找不到下一步；
2. 知道最终目标，但不愿自己串联检查项目、新词挖掘、翻译、修复、任务跟踪和工具等复杂
   流程。

理想体验不是让用户学习内部术语，而是让她描述结果：

> 检查 ABC Mod 有没有更新；如果有，先跑新词挖掘机，再做增量翻译，最后生成一张新封面。

助手负责提出一份能被普通用户看懂的计划，Remis 负责安全执行。

## 它能做什么

Copilot 可以：

- 根据用户文档解释功能、错误和操作顺序；
- 结合经过清理的当前页面／项目上下文回答；
- 检查项目和任务的只读状态；
- 提出下一步建议和安全导航按钮；
- 不确定时明确说不知道，并引导用户查看任务、日志或反馈问题。

Agent 可以：

- 把用户目标拆成 Remis 已注册的工作流步骤；
- 读取完成规划所需的有限项目状态；
- 展示项目、语言、模型、步骤、费用／写入风险和预期结果；
- 在用户批准后，把不可变计划交给 Remis 的现有业务代码执行；
- 使用准确任务 ID 跟踪执行，最终汇报做成了什么、没做成什么。

## 它不能做什么

助手不是 Codex 一类万能电脑 Agent。它只能使用 Remis 内部明确注册并治理的能力。

模型本身不得：

- 直接修改本地化文件、词典、数据库或任意用户文件；
- 直接调用未注册的 Python 函数、Shell、系统命令或网络接口；
- 修改 Remis 源码或给已安装客户端打补丁；
- 访问或回显 API key、Cookie 等秘密；
- 操作 Steam 账号、Paradox 启动器或未纳入 Remis 的第三方应用；
- 发明不存在的功能或 action；
- 绕过所属功能已经建立的确认门。

真正产生副作用的永远是 Remis 业务代码，不是语言模型。

## 计划与执行

```text
用户自然语言目标
  → Copilot 回答或 Agent 提议结构化计划
  → Remis 校验 action、参数、顺序和权限
  → UI 展示完整计划与风险
  → 用户批准
  → Remis 业务工作流执行
  → Task Center 持久化状态
  → 助手按真实终态汇报结果
```

模型只能提供建议。未经 Remis 校验和用户批准的模型输出没有执行权。

## 哪些操作需要确认

无需确认：

- 只读回答；
- 读取经过授权和清理的项目／任务摘要；
- 打开 Remis 页面；
- 生成但不执行计划。

任何包含实际执行的计划，都必须在开始前作为一整份计划确认一次。确认页面必须完整展示：

- 所有步骤及执行顺序；
- 可能产生费用的模型调用；
- 将创建、复制、写入、覆盖或删除什么；
- 使用的项目、语言、供应商和模型；
- 部署等普通执行步骤。

付费调用和部署都由这次整份计划确认涵盖。部署不是需要在执行到该节点时再次确认的高风险
操作。

计划开始后，只有新增步骤或扩大已经展示的执行范围时才必须暂停并重新确认。参数变化若
没有扩大范围，仍必须由 Remis 校验，但不应为了实现细节反复打扰用户。

Agent 没有通用“修改原始 Mod／创意工坊文件”能力。Remis 没有注册的功能必须直接拒绝，
不能生成一个确认框把不存在的能力变成可执行动作。删除等已有功能是否需要模块自己的额外
确认，继续服从对应功能契约，不由 Agent 擅自取消。

## 怎样才算成功

“请求已接受”“计划已批准”或“任务已启动”都不算最终成功。

助手必须：

1. 保存每个实际任务的准确 ID；
2. 等待或重新读取持久化终态；
3. 逐步说明哪些完成、哪些跳过、哪些失败；
4. 对部分成功明确指出可用成果和剩余问题；
5. 给出用户可以采取的下一步；
6. 不能把没有证据的推测写成“已经完成”。

复杂计划只有在所需步骤达到计划定义的终态后才算完成。若“检查更新”发现没有更新，按
计划跳过后续步骤也可以是正常成功，但必须说明为什么没有执行。

## 系统绝不能偷偷做什么

- 未批准就产生模型费用或写入；
- 把计划建议伪装成已执行结果；
- 计划执行中静默增加步骤或扩大已经批准的范围；
- 在已批准计划之外自动部署、删除成果或清理文件；
- 失败后无限重试；
- 把部分成功说成全部成功；
- 因聊天历史存在就长期保留对磁盘的写权限；
- 让模型输出绕过 Action Registry 直接成为函数调用。

## 当前与未来

3.1.0 中：

- 普通打包版关闭助手前端；
- 普通打包版不注册 `/api/copilot`；
- 开发态已有帮助问答、白名单导航、只读规划和“创建项目 + 初次翻译”批准流程；
- 尚不能完成通用多步骤编排，也不会在聊天中可靠等待并总结任务终态。

下一版本目标是向普通用户开放第一版，优先把文本模型、用户文档、动作说明、确认语义和
结果表达准备可靠。不能因为目标是公开就把尚未支持的复杂流程写成现成功能。

长期愿景是有限域工作流编排：用户可以放心委托复杂 Remis 任务，模型负责理解与规划，
Remis 负责校验和执行，人类保留最终批准权。

## 本阶段明确不做

- 通用电脑 Agent；
- 自由文件编辑；
- 修改 Remis 源码；
- 操作 Paradox 启动器或加载顺序；
- 无确认自治运行；
- 在业务代码没有对应能力时让模型“模拟完成”；
- 用聊天黑盒取代 Task Center、项目页面和各功能的确认界面。
