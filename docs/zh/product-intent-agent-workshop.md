# 智能工坊：产品意图契约

这份文档描述 Remis 为什么需要格式修复安全护栏、哪些问题允许自动修复，以及为什么
“自动写回”不等于允许模型自由改写译文。当前实现与差距见
[智能工坊开发契约](developer/agent-workshop-contract.md)。

## 文档状态

- 产品状态：稳定正式功能
- 适用范围：初次翻译、增量翻译或现有项目译文中的可检测格式错误
- 产品决定人：玲珑
- 首次确认：2026-07-30
- 当前方向：维持稳定、观察缺陷；暂无功能扩张计划
- 用户指南：[智能工坊](user-guides/agent-workshop.md)
- 相关背景：[Issue #34：源语言标点残留](https://github.com/Drlinglong/Remis/issues/34)

## 用户为什么需要它

翻译提示词已经要求模型保留变量、闭合标签并使用目标语言标点，但模型仍可能不遵守。
这些错误会破坏显示、游戏语法，甚至影响联机同步。因此 Remis 需要在翻译后增加一层独立
安全护栏。

随着模型遵循指令的能力提高，智能工坊的使用频率可能下降，但这不是裁撤理由：

> 公路越来越安全，不代表汽车不再需要安全带。

智能工坊负责模型偶发犯错时的最后一道格式保护，不负责重新评价整篇译文。

## 负责修什么

允许进入自动修复流程的问题必须先被确定性规则检测出来，包括：

- 变量、占位符或游戏命令损坏、缺失、数量不一致；
- 颜色标签、格式标签缺失或没有正确闭合；
- 引号等本地化文件结构错误；
- 译文残留源语言标点，例如 Issue #34 中中文标点残留在英文译文；
- 其它已经拥有明确验证规则、能在修复后重新判定通过／失败的格式错误。

智能工坊不负责：

- 文风、语气、氛围；
- 主动寻找没有格式错误的普通错译；
- 为了个人风格偏好自由重写整句；
- 增删没有被格式规则要求的内容；
- 重翻整份文件；
- 修复损坏的 localization key。

进入工坊的门票仍然是确定性格式规则命中，但模型可以审视这条完整句子。原因是 Remis
送入前只能确认“这条有格式错误”，无法知道它究竟只是把 `[concept]` 错译成了 `[变量]`，
还是连句意也同时翻错。后一种情况很罕见，但既然模型已经在修这条内容，顺手纠正明确的
误译、遗漏或生硬表达属于可接受恢复。

这项许可不意味着工坊会主动扫描语义质量，也不允许修改没有格式问题的其它条目。纯文风、
术语管理和项目级校对应分别交给校对、术语表或重新翻译。

## 用户什么时候会想到它

默认流程是：

1. 初次翻译或增量翻译生成译文；
2. Remis 扫描格式问题；
3. 若存在可修问题，自动进入内嵌格式修复；
4. 有限重试后报告修复数量和剩余问题。

用户也可以主动打开“质量与术语 → 格式修复台”，为已有译文重新扫描和修复。

它不是部署的必经人工步骤；没有检测到问题时无需调用模型。

## 用户真正要得到什么

用户要的是已经修好的翻译文件，不是另一份建议清单。Remis 应当：

- 只把被检测出的条目发送给修复模型；
- 允许模型在修复格式时审视该条完整句子；
- 只接受最终通过格式验证的候选；
- 自动逐条写回对应译文；
- 保持文件中其它条目不变；
- 最后重新扫描并报告仍然存在的问题。

让用户逐条审批变量、标签或标点修复，是对用户时间的浪费。自动写回是本功能的设计目标。

## 开始前必须确认什么

独立进入格式修复台时，真正调用模型和写文件前必须确认：

- 当前项目；
- 本次待修条目数量和范围；
- 供应商；
- 模型；
- 本次调用可能产生费用并会自动写回通过验证的条目。

内嵌工坊属于用户已经确认的翻译流程。默认沿用该次翻译的供应商、模型和性能设置；用户
可以在高级设置中关闭内嵌工坊，或改用独立模型配置。

确认的是“让 Remis 自动修复这批明确的格式问题”，不是逐条确认修复结果。

## 怎样才算成功

每个条目独立判断：

1. 模型返回候选；
2. 确定性验证确认目标错误已经消失、必要变量和标签仍然正确；
3. Remis 只替换对应 key 的译文值；
4. 写回后能读回相同内容并再次验证；
5. 最新扫描不再报告该问题。

全部问题消失时为完全成功。有限重试后仍有问题时允许部分成功：

- 已通过验证的修复保留；
- 未通过的条目继续留在问题列表；
- 用户看到成功数量、剩余数量和受影响条目；
- 用户可以再次进入格式修复台，或换模型／人工处理。

## 自动覆盖的精确边界

智能工坊可以覆盖当前译文，但只限于同时满足以下条件的条目：

- 该条目由格式规则明确检出；
- 用户已批准本次项目、问题范围、供应商和模型；
- 修复候选通过确定性验证；
- 写回目标是 Remis 管理的翻译成果，而不是原始 Mod 或创意工坊文件；
- 只替换该 key 的译文值，不动其它条目。

因此，“不能覆盖人工译文”不是本模块的绝对规则。用户主动运行格式修复台，就授权 Remis
修复选定范围内的损坏译文，并允许模型纠正同一条中的明显语义问题；但这项授权不能扩张
到未检出的人工修改、其它条目或不受约束的风格重写。

## 术语保护

整句审视带来一个真实风险：工坊当前没有翻译流程使用的词典上下文，可能在修格式或明显
错译时把正确术语改掉。

长期契约是：

- 格式修复不能把项目词典、手选词典或全局词典中已经适用于当前语境的正确术语洗掉；
- 内嵌工坊应尽量继承本次翻译实际使用的词典快照和优先级；
- 独立工坊需要能够取得该项目当前有效的词典约束；
- 词典仍然是优先指导，不应把有语境限定的词条机械替换到错误语境；
- 在词典上下文尚未接入前，必须把术语漂移视为已知风险并通过测试和抽查观察。

具体词典载荷、快照时点和冲突处理仍需 Agent 核验实现后共同确认，不能在文档里凭空发明。

## 有限重试与失败

Remis 可以在固定上限内，对仍未通过验证的条目再次调用模型，并把最新验证错误反馈给
下一次尝试。到达上限必须停止，不能无限产生费用。

反复失败通常意味着：

- 当前模型能力不足；
- 错误超出自动修复范围；
- 源上下文缺失；
- key 损坏或目标文件无法可靠定位；
- 写回或重新读取失败。

再次进入格式修复台相当于用户发起新一轮处理；不能在后台无限重试。

## 系统绝不能偷偷做什么

智能工坊绝不能：

- 修改未被本次扫描选中的条目；
- 主动扫描或修改只有语义问题、没有格式问题的条目；
- 借“顺手纠错”自由改写文风；
- 重翻整份文件；
- 修改 localization key；
- 修改原始 Mod 或创意工坊文件；
- 自动部署；
- 无限重试或在批准范围外继续调用模型；
- 静默切换供应商或模型；
- 把未通过验证的候选当作成功修复；
- 在最终验证失败后把失败候选留在文件中；
- 因一次失败撤销其它已经独立验证成功的条目。

## Issue #34 的产品结论

Issue #34 最初针对“源语言标点残留在目标语言译文”提出双重保险：

1. 翻译提示词尽量避免生成错误标点；
2. 翻译后使用目标语言感知的规则检测和修复残留标点。

这个问题已经关闭，但其长期价值不是一段针对中文到英文的紧急替换脚本，而是确立了
“提示词预防 + 确定性验证 + 有限自动修复”的安全护栏模式。特殊游戏标记必须受到保护，
不能把所有标点做无上下文的全局替换。

## 当前状态与非目标

智能工坊是稳定正式功能。当前没有升级这套系统的产品计划，只需要长期观察实际错误、
模型表现和稳定性。

明确非目标：

- 文学润色或整篇校对；
- 术语统一；
- 自动修 key；
- 自动部署；
- 对没有规则证据的文本主动找茬；
- 要求用户逐条批准已经验证通过的格式修复；
- 因使用频率下降而删除安全护栏。

## 必须长期保留的契约测试

1. 初次与增量翻译默认启用内嵌扫描／修复，并允许高级设置关闭。
2. 内嵌工坊默认沿用本次翻译的供应商、模型与限制。
3. 没有可修问题时不调用模型。
4. 独立修复必须绑定项目、问题数量、供应商和模型确认。
5. 只把规则检出的条目送入修复；允许审视该条完整句子，但不能波及其它条目。
6. 重试次数有硬上限，只重试仍未通过验证的条目。
7. 候选在写回前验证；写回、读回或最终验证失败时恢复旧译文。
8. 写回只改变目标 key 的值，保留其它行、key 和原始 Mod。
9. 部分成功保留成功项并准确报告失败项。
10. key 损坏不调用自动修复模型，直接说明需要人工处理。
11. 工坊不部署、不重翻文件、不静默切换模型。
12. 源语言标点残留修复保护变量和特殊游戏标记。
13. 整句修订不得破坏当前有效术语；词典上下文接入后必须锁住快照和优先级。
