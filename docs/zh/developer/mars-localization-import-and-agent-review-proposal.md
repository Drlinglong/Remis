# 火星求生 Mod 本地化导入与 Agent 平台化方案讨论稿

日期：2026 年 10 月 14 日。状态：方案讨论稿，供其他 Agent 评审，尚未作为产品架构实施。

Remis 需要面对作者提供的不规范 CSV，以及写在 Lua 中的玩家可见文本。Grom 的实际案例表明，格式解析、源语言选择、代码语义审查和翻译应分别管理。更重要的是，Grom 与此前 `kz4dEz` 的交付都显示：当 Mod 超出固定 workflow 的建模范围时，审查过的知识要么被硬编码进核心流水线，要么由外部 Agent 在 Remis 之外用私有脚本完成。两条路都让审查结论脱离 Remis 的管理。

本稿的核心建议有两层。第一层是本地化数据模型：保留原始 Mod 快照，在可追溯的内部文本记录上翻译；涉及 Lua 改写时，由编程 Agent 审查代码语义，确定性执行器负责应用已审查的补丁并验证。第二层是产品架构：沿着 Remis for Codex 已经确立的“Agent 是自然语言控制面，Remis 是可靠执行面”定位，把执行面从流程级接口扩展为细粒度、可校验的工具面，并通过更完整的 MCP 暴露给外部编程 Agent。

## Grom 案例中的实际问题

原 Mod 为 Grom，作者 GromGor，适用于 Surviving Mars Relaunched，原页面说明提供英文和俄语。原页面：https://steamcommunity.com/sharedfiles/filedetails/?id=3604444917 。本地 Mod ID 为 `DoEpVdS`。

原始 `ModContent.fpk` 已通过现有 FLPK v1 读取器校验；162 个文件可以隔离解包，源包没有损坏。SHA256 为 `0f639d14c7e673de14140e0970ab73c4f9b7390579b56411d38f9fc1a15b6c58`。此结论只涉及读取和解包，不证明游戏运行效果。隔离解包目录位于 `batch-term-workflow-20261005` 工作树的 `.runtime/app/diagnostics/grom-3604444917-20261014`。

`local.csv` 注册为俄语本地化表。表头为 `ID,Text,Translation,VoiceActor,Context`，但正文存在引号前空格及省略末尾空列。Remis 当前严格五列解析首先报出第 2 行列数不符。按标准 Python CSV 解析器改变空格规则后，仍有 2、3、4 列记录，因此仅打开 `skipinitialspace` 无法解决全部问题。解析器报告的多余列有些来自没有识别引号，不能据此认定源表真的具有额外字段。

源表不是完整的英俄对照表：部分 `Text` 是俄语而 `Translation` 为空，另一些行同时包含英文和俄文。文件名、表头或目标语言注册都不足以证明某列统一属于英文。英文大量存在于 Lua 的 `T(id, text)` 默认文本；部分百科文本使用无编号 `T(text)`，还有运行时拼接、动态包装和语言分支。

### 多源文本冲突的实测归因

现有 Lua 分析器在 Grom 上产生 428 个条目（其中 422 个为已有编号的 `T`）和 10 个待审条目。六个条目被标记为多源文本冲突。逐条核对后，没有一个来自动态文本包装：

| 编号 | 实际原因 | 归属 |
| --- | --- | --- |
| `948214972435`、`930100581526` | `Code/techsTrading.lua` 同一函数内 `"unknown tech"` 与 `"unknown name"` 被合并为同一身份，身份上下文均为 `local tech1` | Remis 缺陷：条目身份粒度过粗 |
| `0`、`666000` | 作者把这两个编号当作占位编号，分别被几十条互不相关的文本共用 | 作者惯用写法，不是语义冲突 |
| `666273`、`666277` | 复制粘贴造成编号复用；`666277` 同时用于标题和描述 | 作者真实缺陷 |

因此，冲突标记至少需要区分三类：Remis 身份碰撞、作者占位编号、作者编号复用。候选数也不等于完整覆盖数或实际需要翻译数。

### 本次交付实际绕开了 Remis

为完成 Grom，执行 Agent 在诊断目录中编写了约 12.5 KB 的专用脚本 `prepare_grom_reviewed.py`。该脚本：

- 临时安装 `luaparser` 到 `lua-validation-libs`，因为 Remis 没有正式的 Lua 语法分析依赖；
- 直接导入 Remis 内部函数 `_tokens`、`_literal_text`、`analyze_source`、`quote_lua`；
- 用与 Remis 不同的算法分配 88 个新编号：盐值为 `grom-reviewed-v1`，只以文本为身份；Remis 自身使用 `remis-mars-lua-v1`、Mod ID 和语义身份；
- 在 20 个文件中产生 209 条审查决定，每条只记录路径、起止偏移、替换内容与理由，没有源文件哈希和锚点原文。

209 条决定的理由分布：106 条为等价的 `T` 表调用语法，26 条为保留布局或参数包装、不分配编号，44 条为按钮标题本地化，12 条为拆分共用占位编号的无关文本，12 条为审查后的匿名英文 `T` 文本分配稳定编号，其余为少量回退标签、描述拆分和显示映射。

这些决定在内容上是有价值的语义审查结果，但它们没有进入 Remis 的项目状态：作者更新 Mod 后偏移会全部失效，同一 Mod 存在两套编号来源，下次维护无法知道哪些编号是审查后分配的。

### 已有的同类问题：`kz4dEz`

`scripts/core/mars_pipeline/prepare_source.py` 中存在 `mod_id == "kz4dEz"` 分支、`_shuttle_dedup_profile` 与 `_attach_profile_ids`，把针对单个 Mod 的人工审查结论写成通用流水线代码。该模块已有 584 行，超过 500 行职责审查线。若继续沿用此模式，每个复杂 Mod 都会向核心模块增加一段仅对它有效的分支。

Grom 和 `kz4dEz` 是同一问题的两种表现：固定 workflow 的出口只有“硬编码进核心”或“在外部写私有脚本”。

## 当前能力与边界

本地化数据层的检查对象是 `batch-term-workflow-20261005` 工作树，提交 `ab4e439f2ab2edf55059bccd39bad97228a43636`。该工作树有其他开发中的改动，以下不是对全部正式版本的判断。

现有 `prepare_source.py` 能提取部分带编号的 `T(...)`，并与 `lua_expressions.py` 配合分析直接 `Untranslated(...)`、部分字面量、拼接和格式化表达式。流程具有源码哈希、候选审查、稳定编号、CSV 准备和完整副本导出等基础能力。`rewrite_sources` 已经会在应用前核对文件哈希与片段哈希，是确定性补丁执行器的雏形。普通 CSV 处理位于 `scripts/core/surviving_mars_csv.py`，使用严格的 Python `csv` 解析与精确表头，没有方言层。

条目身份目前由文件名、正则找到的前一个 `function` 声明、前 4 行内最近的 `=` 左侧内容拼成，不包含文本内容。它既会造成上文的同函数碰撞，也会把函数结束后的模块级代码继续归入前一个函数。

“英文在 Lua 中”不意味着全部文本都需要重写。已有编号的 `T(id, text)` 通常可直接由语言表覆盖；没有编号、普通字符串、动态表达式和语言分支则需要进一步理解用途。现有扫描不具备全程序语义分析能力，也不能保证没有遗漏。

Agent 接入层方面，Remis 已经具备：

- Remis for Codex 产品定位（https://drlinglong.github.io/Remis/codex/）：“Codex is the natural-language control plane. Remis is the reliable execution plane.”，以及本机 API、审批门槛、持久状态等安全边界；
- `/api/agent` 下的项目检查与导入、任务计划与启动、校验、重试、修复、导出预览与批准、基线同步、工坊、术语、增量、质量等路由，以及火星 `mars-pipeline` 准备、运行、导出路由；
- `scripts/mcp_adapter/` 中的 MCP 适配器，目前只暴露 7 个工具：`preflight`、`capabilities`、`list_projects`、`inspect_project`、`create_translation_plan`、`start_approved_plan`、`get_job`；
- 应用内 Copilot（`scripts/core/copilot/`，基于 PydanticAI），使用 Remis 自有的只读工具做流程规划与推荐。

缺口在粒度：现有接口都是流程级的，“导入、计划、启动、校验、导出”。当任务需要读懂一段 Lua、提出一个改写、申请一个编号时，没有对应的工具，Agent 只能导入内部函数或自己实现。

## 外部参照：General Translation

General Translation（GT，https://generaltranslation.com）与 Remis 类似，提供翻译、术语表、上下文和翻译工作流。以下结论来自官网文档与开源仓库 https://github.com/generaltranslation/gt （MIT 许可，阅读时提交 `c34431b`，2026-10-12）的只读审阅，未安装或运行其代码。

GT 的组成包括开源库（`gt-next`、`gt-react` 等，以 `<T>` 包裹界面文本）、CLI、平台 API 与 Dashboard、托管 MCP 服务器，以及名为 Locadex 的 i18n Agent。官网说明 Locadex 在用户的 GitHub 仓库中改写源码、开 PR，由人审查合并。开源仓库中的 `packages/locadex` 只是一个打开 Dashboard 网页的启动器；仓库内没有 Agent 循环、系统提示、工具白名单、变更验证或开 PR 的代码。`.mcp.json` 只指向远程 `https://api.gtx.dev/mcp`，MCP 服务器实现也不在仓库中。也就是说，GT 开源的是内核（库、身份哈希、锁文件、CLI、代码改写），Agent 与翻译服务是闭源托管服务。

开源仓库无法说明 Locadex 的运行时、上下文管理与工具编排有多复杂；闭源不代表简单，它很可能是 GT 投入最大的部分。仓库能说明的是：GT 把身份哈希、锁文件、改写规则做成了确定性、与具体 Agent 无关的能力，因此无论由哪个 Agent 执行，结果都可以验证。这一点与运行时的复杂程度无关，也是 Remis 当前最缺的部分。

可以直接借鉴的具体设计：

| GT 设计 | 位置 | Remis 对应用途 |
| --- | --- | --- |
| 内容身份哈希：对 `{source, id, context, ...}` 做键排序序列化后取 SHA-256；可选字段仅在有值时加入，新增字段不改变旧哈希 | `packages/core/src/id/hashSource.ts`、`utils/stableStringify.ts` | 文本记录的原文变化检测；与冻结的发布编号分离 |
| 锁文件：每个文件的 `versionId` 是其全部字符串哈希排序后的哈希；每个语言产物记录 `postProcessHash`，本地哈希不符即视为人工修改，不覆盖 | `packages/cli/src/fs/config/downloadedVersions.ts`、`api/collectUserEditDiffs.ts` | 补丁库记录应用后文件哈希；作者更新或重译时发现人工修改即停止，不覆盖已校对译文或手工调整 |
| 单一的“有意义文本”判断（含 Unicode 字母或数字）与显式函数名白名单 | `packages/cli/src/react/jsx/evaluateJsx.ts`、`packages/python-extractor/src/constants.ts` | Lua 调用白名单与游戏 API 契约表集中在一个模块，Agent 通过 MCP 调用同一实现，不再自行实现 |
| 改写规则写成规格文档（15 条插入规则） | `packages/compiler/src/processing/jsx-insertion/JSX_INSERTION_RULES.md` | 编写《Lua 改写规则》，内核按规格校验，Agent 按规格提案 |
| 随 CLI 分发给用户 Agent 的写法说明；仓库内按路径限定作用域的规则文件 | `packages/cli/src/setup/instructions/gt-react.md`、`.claude/rules/` | 按游戏拆分规则，作为 MCP resources 分发，而不是全部写入一个 Skill |

GT 的 Python 提取器使用 tree-sitter，可作为 Remis 选择 tree-sitter-lua 的先例。

不应借鉴或需要反向处理的：

- GT 的 ICU 变量会被编号为 `{_gt_1_}` 一类形式。Remis 永久禁止在发送给 LLM 的文本中把有语义的标记替换为通用占位符；编号形式最多只能用于内部哈希计算。
- GT 仓库内的本地校验只检查 ICU 或 MDX 能否解析，没有找到检查译文是否保留变量和标签的代码（若存在应在服务端）。Remis 现有的标记保留校验是优势；补丁执行器还应在改写前后各解析一次 Lua，比较字符串与变量清单，任何丢失均拒绝。
- GT 编号取 SHA-256 前 16 位十六进制，适合做身份标识，不适合补丁完整性校验；Remis 补丁一律使用完整 SHA-256。
- GT 的编译器与 CLI 各自实现同一套插入规则以保证哈希一致，存在两份实现逐渐偏离的风险。Remis 应坚持单一实现，经 MCP 暴露。

不能照搬的有两点，它们也是 Remis 的真正难点：

1. GT 处理的是用户自己的代码，有版本控制、构建、CI 与 PR 审查作为安全网。Remis 处理第三方 Mod：没有测试、没有构建、游戏不能自动运行、作者随时更新。GT 交给 Git 的那部分，Remis 必须自己承担：源码快照、带锚点的补丁记录、更新后的可重放性。
2. 网页应用每次构建都可以重算字符串身份。Remis 生成的编号会进入玩家存档、被其他 Mod 引用、随工坊版本发布，一经发布就必须冻结。Remis 需要编号台账，而不是可随时重算的内容哈希。

## 平台架构建议

### 定位（已确定）：外部 Agent 加完整 MCP，不自建 Agent 运行时

用户于 2026 年 10 月 14 日确定以下方向：

- Remis 不自建通用 Agent 运行时。通用运行时（循环、上下文窗口管理、工具调用编排）方面，Remis 作为单人维护项目难以超过 Codex 与 Claude Code。
- 最现实的路线是把 MCP 做完整，使 Codex、Claude Code 等外部 Agent 能熟练进入 Remis 工作，而不是每次都要改动 Remis 才能勉强完成任务。
- 目标用户包括会使用编程 Agent 的进阶用户，也包括普通玩家：安装 Codex 或 Claude Code 已不复杂，普通用户可以直接用自然语言说“我想玩这个 Mod 的某语言版本，都交给你了”，由 Agent 通过 Remis 完成并交付。这延续了 Remis 让普通人点几下就能用母语玩上喜欢的 Mod 的初衷，只是入口从鼠标点击扩展为自然语言。
- 应用内 Copilot 保持只读引导与规划角色，与 MCP 共享同一套工具注册与权限定义，避免出现两套能力描述。

Remis 在这一方向上并非从零开始：各类校验器、术语系统、审批门禁、持久任务状态、`/api/agent` 和 Remis for Codex 已经构成了可靠的基础。本稿中的“内核”就是指这类不依赖模型判断、对同一输入给出同一结果的部分；“合同”指 Agent 与 Remis 之间的接口约定：工具名称、输入输出结构、错误码与状态、审批规则，以及写给 Agent 的 Skill 和规则文档。需要补上的是面向源码改写的那一块：文本记录、编号台账、补丁与审查决定的存储，以及对应的细粒度工具。

领域相关的 Agent 逻辑仍须由 Remis 负责，因为通用运行时不了解游戏格式：为单条审查组装上下文（调用位置、游戏 API 契约、术语、作者对照，可提供为 `remis_review_context` 一类工具）、大批量条目的任务拆分、审查流程与评测样例。

面向普通用户时，Skill 与 MCP 的说明必须假设对方不懂技术：由 Agent 用通俗语言解释每个需要批准的步骤，付费、导出、覆盖与上传仍逐项请求批准。

### 三层结构

| 层 | 职责 | 现状 |
| --- | --- | --- |
| 内核（确定性，Remis 所有） | 源码快照与哈希、文本记录库（身份、来源、源语言依据）、编号台账、补丁库与执行器、各类校验器、翻译引擎（术语、格式修复、批处理、Paradox 标记保护）、预算、授权与导出门禁 | 翻译引擎与审批门槛成熟；补丁库、编号台账、文本记录来源模型缺失 |
| 工具面（`/api/agent` 与 MCP） | 细粒度操作：解析 Lua、查询文本记录、提交与校验补丁、申请编号、计算覆盖率、翻译指定子集 | 只有流程级接口；MCP 只有 7 个工具 |
| 配方（workflow） | Paradox 固定流程保留；火星复杂 Lua 由 Agent 在工具面上组合完成；配方写入 Skill | 全部为固定流程 |

核心原则：Agent 提案，内核裁决与落地。Agent 可以自由读取、分析和提出修改；所有改变持久状态的操作必须经过内核，由内核核对源文件哈希、锚点唯一性、Lua 语法、标记完整性和编号台账，再记录并执行。MCP 只是 `/api/agent` 之上的薄适配层，不承载业务逻辑：同一份合同，两种传输方式。

Grom 脚本导入的那几个内部函数，基本就是工具面目前缺失的接口清单。

### 内核新增能力

**补丁库与执行器。** 把 `rewrite_sources` 泛化为通用执行器，并把补丁从代码变成项目数据。每条补丁记录至少包含：Mod 来源及版本、目标文件路径与源文件哈希、锚点原文及其哈希、可选的语法节点路径、替换内容、所属文本记录或编号、修改理由、证据（使用位置、调用链、契约依据）、提案者、审查状态与审查者。执行前重新核对哈希；作者更新后，锚点能唯一匹配的补丁可重放，匹配失败或语义变化则回到审查队列。`kz4dEz` 的硬编码和 Grom 的 209 条决定作为首批迁移对象和验收样例。补丁库应作为独立的 repository 与 policy 模块实现，不向 `prepare_source.py` 继续添加职责。

**审查决定的持久化与复用。** 这是本方案最优先的目标：Agent 第一次审查得出的结论必须保存下来，否则每次作者更新都会让 Agent 重新探索整个 Mod，浪费大量时间和费用。Grom 的 209 条决定就是反例：它们只记录了偏移量，作者一更新便全部失效。

需要保存的不只是“改了什么”，也包括“决定不改什么”。Grom 中有 26 条决定是“保留布局或参数包装、不分配编号”；如果只保存补丁，下次 Agent 仍会重新调查这些位置。审查决定应覆盖：

- 改写决定：对应一条补丁；
- 不改写决定：例如内部枚举、日志、路径、比较用字符串，记录原因与证据；
- 源文本选择决定：选用 Lua 默认文本、CSV 文本或人工对照的依据；
- 作者缺陷处理决定：占位编号或编号复用是否拆分；
- CSV 方言解释决定：某行按哪条兼容规则解释。

每条决定绑定可重新定位的锚点：目标文件、玩家可见文本、结构化语义上下文（所属对象、类或函数、字段或参数名）、代码片段哈希（仅作变化提示）、可选的语法节点路径，以及作出决定时依赖的证据位置（例如“该值只被传给 `display_name`”所依据的调用点）。锚点规则见“讨论结论”第 1、8 条。

作者更新 Mod 后，Remis 按以下顺序处理，Agent 只需处理变化部分：

1. 文件哈希未变：该文件内全部决定直接沿用，不需要 Agent 参与；
2. 文件已变但锚点与证据位置都能唯一重新定位且内容未变：自动沿用，记录为“重新定位后沿用”；
3. 锚点找到但周边证据变化，或锚点不唯一、找不到：进入重新审查队列，并附上旧决定、旧理由和新旧代码差异，Agent 在旧结论基础上判断，而不是从零开始；
4. 新出现的候选：进入首次审查；
5. 已消失的条目：决定归档，已发布编号在台账中保留并标记退役。

每次更新结束时报告“沿用 N 条、重新定位 M 条、重新审查 K 条、新增 J 条、退役 R 条”，使维护成本可以被看见。一个 Mod 的审查成本应主要发生在第一次，后续版本只为变化付费。

**编号台账。** 每个 Mod 一份，只有一个分配器。每个编号记录来源：作者原有、Remis 生成、审查后分配；记录绑定的文本记录身份、首次发布的版本。发布后冻结，后续只以台账为准，不再重新推算；碰撞消解不能悄悄改变已发布身份。作者占位编号（如 `0`、`666000`）与作者编号复用作为独立的缺陷类别记录，由审查决定是否拆分。

**文本记录与来源模型。** 内部条目携带 Mod 来源及版本、源文件哈希、语法节点或源码范围、原文本、选定源语言及依据、已有或新分配编号、运行时参数、使用场景和审查状态。每条记录保存候选来源列表，例如 `source_candidates: [{origin: lua_default | csv_text | csv_translation, script: latin | cyrillic, text}]`，并记录选中项与选择规则。条目身份改用语法树路径（函数全名、语句锚点如赋值字段名或调用名加参数序号、同级序号），文本内容哈希单独保存。

**游戏 API 契约表。** 记录哪些属性和函数接收显示文本（如 `display_name`、`description`、通知标题等）。它是规则批准的依据，也是 Agent 审查时的参考资料，可作为 MCP resource 暴露。基础游戏语言表作为参考数据导入，用于判断编号是否属于基础游戏；现有硬编码的 `_SHARED_GAME_IDS` 不足以承担这一职责。

### 审查分级

- 已有编号的 `T(id, text)`：不改代码，不需要审查。
- 字面量直接进入契约表中的显示属性：按规则批准；规则附带 Lua 样例和回归测试。
- 其余情况：编程 Agent 审查，产出带证据的补丁记录。

规则只能通过代码变更加测试新增，Agent 运行时不能自行提升规则。首次识别不能自动等同于安全授权。LLM 不应自由重写整个 Lua 文件，也不应在翻译时改变函数名、内部选项、控制流和玩家存档字段。

## 兼容导入的设计

导入层接受经过验证的源文件格式变体，内部记录和输出保持严格约束。原始文件字节、源码位置及所有非翻译字段必须保留；兼容解释写入独立记录，不覆盖作者的源文件。

CSV 方言放在火星求生专用适配器内，不做成统一导入层。兼容标准应是“游戏自身加载器如何读取”，而不是“Python 能否读取”：如果游戏读取引号前空格时同样错位，这份表在游戏内本身就有缺陷，Remis 不应把它“修好”后当作作者原意。实现上建议使用一个小型逐字符读取器，每种偏差对应一条具名规则并记录，而不是在 `csv` 模块上叠加开关。

| 情况 | 处理规则 |
| --- | --- |
| 明确省略末尾空列 | 仅在 ID 合法、Text 引号正常闭合、缺失的恰为末尾列时补空，并记录来源与规则 |
| 引号前空格 | 使用经过样本与游戏加载行为验证的方言规则，不全局删除有语义的空格 |
| 超过五列 | 拒绝；通常来自未识别的引号 |
| 源语言不统一 | 每条记录追踪语言来源，选择明确的英文 Lua 默认文本或已审查对照；禁止静默语言回退 |
| 引号不闭合或字段归属不明 | 阻断该记录或交人工审查，不能用模型猜测补齐 |
| 重复编号或不同默认文本 | 保留全部出现位置，区分 Remis 身份碰撞、作者占位编号、作者编号复用与参数包装 |

兼容解析首先应定义支持的格式及拒绝条件；不能通过忽略错误、丢弃列或修改校验上限来提高成功率。读取失败、语义不明和已成功解析是不同状态。若允许部分导入，项目和导出必须显式标为部分覆盖，不能显示为完整完成。

对于以英文 Lua 为源的交付，作者的俄语表可以按原字节保留，只在交叉核对“仅存在于 CSV 的文本”时解析。CSV 解析失败不应阻断英文到其他语言的翻译。

## Lua 改写需要语义审查

用户明确指出：即使 `T("英文")` 的语法很简单，自动分配编号并替换调用仍可能造成意外。语法形状不能证明该值只用于显示，也不能证明编号、作用域、语言分支和运行时调用均安全。

因此，由工作流先发现候选，再由编程 Agent 沿使用位置检查：它是玩家文本、日志、路径还是内部枚举；是否参与逻辑比较、表索引、去重或存档；是否位于原有俄语分支；编号是否与游戏及其他 Mod 冲突；参数与标签是否保持语义。审查结果需要描述批准的改写及证据，不能仅输出一个无解释的置信分数。

Lua 分析建议改用能给出语法树与字节位置的解析器，例如 `luaparser` 或 tree-sitter-lua；Grom 脚本已经用 `luaparser` 做过语法检查。需要先用真实 Mod 统计 Haemimont Lua 的解析成功率，解析失败时退回现有分词器并显式标记。静态分析可以给出 Mod 内的定义与使用位置；值是否进入存档、是否被动态分派使用，静态分析无法保证，只能依靠审查与实机测试。

## 交付与验证

已有编号足以覆盖目标文本时，生成依赖原 Mod 的语言补丁。必须修改 Lua 才能满足覆盖范围时，制作完整副本，保留原作者署名与来源，明确不能与原版同时启用。新 Mod ID、代码命名空间、资源路径、存档引用和其他 Mod 集成均需要检查；静态通过不能证明存档迁移兼容。

验证应分别报告：源文件读取与解释、文本覆盖、Lua 语法与补丁范围、编号及标签完整性、翻译质量、语言注册和包结构、实际游戏加载与关键功能。任务接受、翻译文件生成、部署完成和 Steam 上传成功应有各自的证据和状态。只有“待审查”与“无法解析”均为零时才能标为完整本地化；否则允许导出，但状态为部分覆盖，工坊说明中写入覆盖率声明。

## 讨论结论（2026 年 10 月 14 日）

以下问题已由用户回答并经讨论确认，作为后续设计依据。

**运行时路线。** Lua 审查等高风险功能面向会使用 Codex、Claude Code 的用户，包括通过自然语言委托 Agent 的普通玩家；Remis 不自建 Agent 运行时，优先完善 MCP。

**1. 审查决定的锚点。** 以玩家可见文本为主键，辅以语义上下文。语义上下文分两层：用于匹配的一层必须可机械计算，即所属对象（如 `PlaceObj` 的类与 `id`、`DefineClass` 名称、函数全名）与字段或参数名；模型生成的用途描述（例如“某建筑在建造菜单中的名称”）只作为说明与证据保存，不参与匹配，因为它不具备确定性。匹配顺序：文本与结构化上下文唯一命中则沿用；文本重复时用上下文区分；仍无法区分则重新审查。代码片段哈希不作为主键，只作为“代码已变化”的提示，以适应 Mod 随游戏更新调整语法而文本不变的情况。

**2. 直接导出的条件。** 用户明确要求交付时，Agent 记录结论并直接导出可游玩副本，不要求玩家校对译文。Remis 做的是 Mod 本地化，不是文学研究，多数玩家也没有能力或意愿校对另一种语言。代码改写的门槛是机器验证而非人工确认：Lua 语法、标记完整性、编号台账检查必须通过。无法确定安全性的条目保持原文，不阻塞交付，以保证直接交付在任何情况下都不会损坏 Mod。交付说明保持简短，用几句话说明主要取舍与修正，用户追问时再展开；说明中必须包含覆盖率与保持原文的条目数。“修正源 Mod 缺陷”只限于文本缺陷：编号混乱（占位编号、编号复用）、文本语法错误、特殊格式或标签错误等；不修改 Mod 的游戏逻辑。

原 `AGENTS.md` 中的 “Leave ambiguous text for human review” 与 Remis Skill 中的 “Keep ambiguous translations for human review” 是开发 Remis 时期的规则，不适用于普通用户，维护者本人也无力逐条审核，已于 2026 年 10 月 14 日删除。

**3. 编号冻结。** 首次导出即冻结，因为许多玩家导出后只在本地游玩。编号永不删除、永不复用，不做主动退役；当前版本不再使用的编号只标记为“当前版本未使用”，查询工具默认过滤，不增加 Agent 的上下文负担。

**4. MCP 粒度。** 细到业务操作，并支持批量：一次取得一批候选及其上下文，一次提交一组补丁提案，一次验证整个补丁集，批量预留编号。批量结果逐条返回，允许部分成功，失败时给出具体问题，Agent 只修失败部分。提交需幂等，重复提交同一提案不产生重复记录；大批量结果分页。Grom 与 `kz4dEz` 仍作为粒度的验收案例。

**5. 游戏 API 契约表。** 由项目维护者维护，依据游戏源码、官方文档与社区 Mod 开发资料验证。从基础游戏 Lua 自动提取初稿；需验证 Haemimont 引擎的类属性定义是否以 `translate = true` 一类标记声明可本地化字段，若属实则大部分条目可机械提取，维护者只需补充例外。

**6. 应用内 Copilot。** Copilot 始终保持只读问答角色。随着 MCP 增强，单独维护 Copilot 的价值下降，教程与帮助功能应并入 MCP（resources 与 prompts）。步骤：先冻结 Copilot 新功能，再迁移帮助内容，最后评估是否移除，避免影响尚未安装外部 Agent 的用户。

**7. 源语言。** 每个项目只有一种源语言，在项目开始前确定；Remis 可通过检查代码判断最可能的源语言。剩下的问题是“缺少源语言原文的条目如何处理”，可按规则机械解决。Grom 中有 39 个 CSV 编号在 Mod 内找不到英文原文：9 个属于基础游戏编号（如 `298`、`7634`、`11231`），作者在俄语表中改写了基础游戏文本，其英文原文需从基础游戏语言表获取；28 个未被 Lua 引用，可能是旧版本遗留或在 Lua 以外引用，尚未逐一核实；2 个在 Lua 中被引用但没有英文默认文本。处理原则：尊重原 Mod 的现状，不替作者补全。原 Mod 只提供了俄语表，其他语言的玩家本来就看到游戏的回退结果，Remis 的译本保持同样行为即可：

- 基础游戏编号：不提供覆盖。目标语言玩家看到的是游戏官方该语言的文本（若游戏支持该语言），与原 Mod 对非俄语玩家的效果一致；作者只为俄语做的改写不扩展到其他语言。
- 未被引用的编号：不会显示，忽略。
- 被引用但没有英文原文的 2 个编号：保持原 Mod 现状，不从俄语转译。

这些条目只在需要时于详细报告中列出，不进入面向玩家的简短交付说明。待验证：火星求生对注册为俄语的 Mod 语言表在其他语言下的回退行为，应在游戏中确认一次。

**8. 重新定位范围。** 不使用字符窗口，改用第 1 条的结构化上下文（所属对象、类或函数、字段名）。文件其他位置的无关修改不会影响这些上下文，因此不会误触发重新审查；对象或字段改变时语义可能已变化，本就应当重新审查。另需检查决定所依据的证据位置（例如“只传给 `display_name`”的调用点）是否仍然存在。效果通过在 Grom 源码上人为修改若干处进行模拟，统计沿用与重新审查的比例。

## 仍待讨论的问题

1. Haemimont 引擎是否以 `translate = true` 等属性元数据声明可本地化字段？需在基础游戏 Lua 上验证。
2. Grom 中 28 个未被 Lua 引用的 CSV 编号来源为何？是否存在 Lua 以外的引用路径（如 `items.lua` 中的 Mod 编辑器对象）？若存在，这些编号会显示，需要纳入翻译范围。
