# Task Center：产品意图契约

这份文档描述 Task Center 为什么存在、它与业务结果页和主页“近期活动”的边界，以及后台任务结束后用户如何继续处理结果。当前实现与差距见 [Task Center 开发契约](developer/task-center-contract.md)。

## 文档状态

- 产品状态：正式功能；3.1.0 首次上线，需持续观察和修补
- 适用范围：Remis 创建的、需要跨页面或跨会话追踪的后台工作
- 产品决定人：玲珑
- 首次确认：2026-07-30
- 当前方向：3.1.x 持续打磨，并为未来 Agent 读取项目运行状态建立可靠基础
- 用户指南：[任务中心](user-guides/task-center.md)

## 用户为什么需要它

用户需要一个不会随当前业务页面一起消失的地方，用来：

- 同时执行多项工作时看清 Remis 正在做什么；
- 发现成功、部分成功、失败或中断；
- 页面或程序关闭后，找回已经完成的任务和结果入口；
- 通过用户日志复核历史工作；
- 明确下一步应该回到哪里继续。

Task Center 不是又一份翻译进度页。它要解决的是跨流程的运行态可见性和结果找回。

## 用户什么时候会打开

- 任务运行中，尤其同时存在多个任务时；
- 离开原页面或重启 Remis 后；
- 看到失败、部分失败或需要批准的提示后；
- 想检查某天执行过的历史任务时。

未来应在任务变成失败、部分失败或中断时给出明显通知，并把用户带到准确的任务记录。3.1.0 目前只有页面内的注意计数与提示，没有独立的失败弹出警告。

## 什么工作应该进入

产品范围尚未最终确认。当前实现已经记录：

- 初次翻译、增量翻译；
- Model Arena 执行与失败参赛者重试；
- Agent Workshop 扫描、修复与子批次；
- 新词挖掘；
- 部署；
- 词典健康检查与合并；
- 内部 Agent dry run 等工程预览任务。

在共同确认范围前，不用“只有长任务”或“所有写操作”替产品负责人下结论。长期判断标准应是：用户离开当前页面后，是否仍需要知道这项工作的执行状态、结果、失败范围或恢复入口。普通文件保存等即时操作不应仅为凑齐历史而制造后台任务。

## 怎样才算任务完成

“流程已经结束”和“用户已经处理”是两个不同维度：

1. 后台流程进入成功、部分成功、失败、取消或中断等终态，就算执行结束；
2. 用户查看并处理结果后，可以点“已处理”，把它移出 Task Center 收件箱；
3. “已处理”不能改变执行结果，也不能删除历史；记录仍应存在于全部日志。

因此失败任务也可以是“已结束”，但绝不能被显示成“成功”。部分成功必须保留自己的业务含义，不能只因统一展示而抹掉。

## 列表与详情的职责

列表按最近活动时间倒序，最新任务在最上方。当前没有把“正在运行”或“需要注意”强行置顶的产品要求；状态标识必须足够醒目。

详情页采用“摘要，不复制业务页面”的原则：

- 首屏回答“当前阶段、结果如何、下一步去哪”；
- 展示足以识别任务的最小上下文：任务类型、项目名称、游戏、创建者、起止时间；
- 保留准确 `taskId`，但技术标识默认折叠；
- 完整语言、供应商、模型、翻译配置和可编辑业务结果仍由所属业务页面负责；
- 下一步必须跳回该任务所属的正确项目与流程，不能只跳到一个模糊的通用入口。

若某类任务仅凭最小上下文无法区分，应补该类任务的摘要字段，而不是在 Task Center 重建整张业务结果页。

## 操作与确认

以下操作如果存在，必须先确认：

- 重试，尤其会再次产生付费模型调用时；
- 取消正在运行的任务；
- 删除历史记录；
- 重新执行整个任务。

“标记已处理”不是删除，可以一键执行，并允许从全部日志恢复。任何重试或重新执行若创建新任务，都必须向用户显示新的任务 ID，并保留与原任务的关联。

## 系统绝不能偷偷做什么

Task Center 绝不能：

- 自动重试付费调用；
- 自动删除或缩短用户可见历史；
- 把失败、部分失败或中断伪装成成功；
- 因展示归一化而丢失业务流程的原始终态；
- 从一条任务跳到错误项目或错误运行；
- 创建重试／重跑任务却不告诉用户新任务 ID；
- 把“已处理”解释为删除任务或业务成果；
- 为了补全摘要去修改翻译文件、项目状态或部署结果。

## 失败或部分成功时最需要知道什么

首屏至少要让非技术用户知道：

- 没有完全成功；
- 影响范围或可理解的失败数量；
- 已有成果是否仍然安全；
- 能否重试、继续或回到哪个页面处理。

统计可以按批次、文件或条目，取决于所属流程已经可靠提供什么，不强制所有任务使用同一口径。技术日志用于进一步诊断，默认折叠，不能取代白话摘要。

## 与主页“近期活动”的边界

主页是摘要工作台，不应同时维护两套近似任务列表：

- **主页正在进行的工作**：从 Task Center 取少量可行动任务，只作摘要和精确跳转；
- **Task Center**：后台任务收件箱，负责运行状态、注意事项、结果找回和“已处理”；
- **全部日志**：按日期查看包括已处理任务在内的任务历史；
- **近期项目变更**：原“近期活动”，只回答“哪个项目发生了什么持久变化”，例如项目状态改变、源版本推进或输出路径登记。

“近期项目变更”不承担实时进度、失败告警、重试或任务结果入口。3.1.0 仍使用“近期活动”这一容易混淆的名称，是待收敛的信息架构问题。

## 当前状态与未来方向

Task Center 是正式功能，但刚上线，存在缺陷的概率不低，3.1.x 预计继续完善。近期重点：

- 增加失败／部分失败通知；
- 稳定不同任务类型的结构化阶段、结果和下一步；
- 收敛主页任务摘要与“近期项目变更”的职责；
- 补齐需要确认的重试、取消、删除和重跑能力时，保持业务流程自己的权限边界。

未来 Agent 应能读取与普通用户相同的可靠任务状态，准确回答“项目里正在发生什么”，但不得因此获得静默重试、取消、删除或修改结果的权限。

## 必须长期保留的契约测试

1. 重启或离开页面后，持久化任务仍可按准确 `taskId` 找回。
2. 列表按最近活动倒序，父任务默认代表一次用户发起的工作，子批次不污染主列表。
3. 终态与“已处理”互相独立；已处理不改状态、不删历史，并可恢复。
4. 失败、部分失败、中断不会显示成成功，也不会显示仍在执行的旧阶段。
5. 详情首屏提供阶段、结果、下一步和最小任务身份，技术诊断默认折叠。
6. 跳转绑定当前任务的项目与流程，不会打开另一条运行记录。
7. 任何付费重试、取消、删除或整次重跑在实现时都必须要求确认。
8. 新重试／重跑任务返回并显示新 ID，且可追溯到原任务。
9. 主页任务摘要复用 Task Center 数据；项目变更流不冒充任务运行流。
