# 项目管理：产品意图契约

项目是某个 Mod 的长期汉化工作空间，不是一次翻译任务。Mod 更新、反复翻译与校对后，
项目仍应保留；它帮助用户始终知道“我在维护哪个 Mod、磁盘现状是什么、下一步去哪里”。
当前实现与差距见[项目管理开发契约](developer/project-management-contract.md)，操作方法见
[项目管理用户指南](user-guides/project-management.md)。

## 文档状态

- 产品状态：稳定正式功能
- 适用范围：项目创建、查看、维护、归档、删除和工作流入口
- 产品决定人：玲珑
- 首次确认：2026-07-31

## 项目身份

- Mod 改名、文件夹移动、Steam 更新，默认仍是同一个项目。
- 一个项目只有一个源语言，但可以在不同翻译流程中产生多个目标语言的成果。
- 目标语言不属于项目固定元数据，不能因为目标语言不同而强迫用户重复建项。
- 同一 Mod 路径不应重复创建项目。当前 sidecar 会冲突，产品上也没有必要；应阻止重复登记。
- 用户可以主动另建项目，但必须选择不同的工作路径，不能让两条记录争用同一份 sidecar。

## 创建时谁决定什么

用户必须亲自决定：

- 项目名称；
- 原 Mod 路径；
- 游戏；
- 源语言；
- 已有译文目录（可选）。

Remis 可以读取元数据和本地化文件，协助猜测名称、游戏和源语言，但只能作为预填建议。
元数据通常不完整，不能静默覆盖用户选择。当前若提供“复制 / 引用”导入方式，也必须由
用户决定。目标语言到翻译工作流再决定。

创建成功后，用户应能核对项目名称、游戏、源语言、实际路径状态、磁盘文件数量与清单，
并看见可执行的下一步。只有这些事实正确，才算 Remis 已经正确认识项目。

## 项目关联的资料

项目可以关联原 Mod 路径、翻译输出、翻译归档与记忆、项目词典、文件级看板状态、
格式校验 sidecar、后台任务、Mod 监控、Model Arena 历史、用户备注，以及未来可选的
最新封面图。

项目不负责记录用户在每个版本校对页面中的每一次手工修改；只有用户明确保存或上载的
结果进入相应存储。部署记录当前不属于项目资料。

## 磁盘是最终事实来源

玩家最终使用的是磁盘上的本地化文件，不是 SQLite 记录。因此磁盘文件、路径和数据库
记录冲突时：

1. Remis 显示冲突及准确路径；
2. 不把缺失目录伪装成空项目，也不自动删除旧记录；
3. 用户确认新路径或磁盘现状后，才以磁盘文件继续；
4. 刷新文件保持只读；只有明确的修复或上载操作可以写 sidecar 或数据库。

## 生命周期与删除

项目只有两种生命周期状态：

- `active`：出现在日常项目列表，正常工作；
- `archived`：退出日常列表，但保留全部资料，可恢复。

删除不是状态，而是永久移除项目记录。删除必须二次确认。若用户选择同时删除磁盘目录，
确认界面必须展示将递归删除的准确路径、给出明确警告，并让该选项默认关闭。Remis 无法
可靠判断某目录是不是自己的工作副本，因此不替用户猜测；最终由用户确认。

删除项目时必须移除项目绑定关系，包括绑定的 Mod 监控和词典关系，不能留下“幽灵项目”。
翻译归档、词典实体、后台任务日志与 Model Arena 记录应按各自存储生命周期保留，不能
仅因项目记录消失而级联清空。

## 操作与确认边界

项目管理承担工作流入口，至少可以进入初次翻译、增量翻译、校对和部署。词典、Model
Arena 和监控可以在各自模块管理，不必占据普通用户的主要下一步。

只有删除项目及可选的磁盘目录需要二次确认。归档、恢复、改名、修改游戏或源语言、替换
源路径、刷新索引、修复元数据、绑定或解除项目词典都不需要额外确认；操作结果必须可见。

未来应提供“最近改动”区域，汇总项目相关任务与文件级结果，但不能靠模糊日志推断成功。

## Agent 边界

Agent 可以在用户给出 Mod 路径后读取元数据和 YML，建议项目名、游戏与源语言；用户确认
计划后可以创建、改名、修改、归档或恢复项目。删除项目及磁盘目录必须单独批准。Agent
不能替用户决定目标语言，也不能把“请求已接受”称为创建完成。

## 明确非目标

- 把一次翻译任务当成一个新项目；
- 为每个目标语言重复创建同一项目；
- 用数据库记录覆盖磁盘事实；
- 因项目归档而删除资料或停止独立的 Mod 监控；
- 删除项目时顺带清空独立任务、归档或 Arena 历史。
