# 校验与常见错误目录（白话版）

> 面向在 Remis 里看到 **校验报错 / 警告**，或翻译结果在游戏中显示异常的用户。  
> 本文解释「这句话是什么意思、你会看到什么、可以怎么做」，**不涉及**修改 Remis 源码。

不同游戏（Vic3 / Stellaris / HOI4 / CK3 / EU4 / EU5…）规则细节不同，但 **出错模式高度相似**。先按「症状」查找即可。

---

## 0. 先分清三种严重程度

| 级别 | 通俗含义 | 建议 |
|------|----------|------|
| **错误 (ERROR)** | 很容易导致游戏崩溃、指令失效、变量显示成乱码 | **优先修** |
| **警告 (WARNING)** | 往往导致颜色/加粗错乱、半截变色、显示难看 | 建议修 |
| **信息 (INFO)** | 提醒你留意，不一定立刻坏 | 有空再看 |

程序闪退、连不上 API 等 **不属于** 本地化格式校验，请看 [日志与诊断](logs-and-diagnostics.md) 和 [FAQ](faq.md)。

---

## 1. 「变量被翻译 / 变量坏了」（最常见高危）

### 你可能看到的提示（大意）

- 变量 / `$...$` / `[...]` 内出现了中文或非英文符号  
- 变量数量不匹配：原文与译文里 `$变量$` 或 `[函数]` 次数不一致  
- 「多出未知变量」

### 白话解释

游戏里有些片段 **不是给人读的句子**，而是占位符或指令，例如：

```text
$COUNTRY_NAME$
[Concept('some_key')]
[SCOPE.GetName]
```

它们必须 **保持原样**（至少内部的 key / 名字不能被翻成中文）。  
如果被翻成「$国家名$」或拆丢了 `$`，游戏就不知道该填什么——这就是常说的 **变量被吞、变量被翻译、变量损坏**。

### 典型坏例子 → 好例子

| 坏 | 好 |
|----|----|
| `欢迎来到 $国家名称$` | `欢迎来到 $COUNTRY_NAME$` |
| `[概念('某某')]` | `[Concept('original_key')]` |
| 原文 2 个 `$FOO$`，译文只剩 1 个 | 译文保留相同数量、相同名字 |

### 你可以怎么做

1. 对照原文，把变量 / 方括号指令 **逐个抄回** 正确形式  
2. 只翻译引号里的 **人类可读句子**，不要翻译 `$...$`、`[...]` 内部的标识符  
3. 在 Remis 中对该条目重新校验；若有「修复选中问题」类功能，可在确认后尝试自动修  
4. 修完后 **再扫一遍**，确认问题消失（而不是只看「好像改了」）

## 2. 图标 / 旗帜 / 概念键被翻译

### 提示大意

- 图标 `@key!` / `£icon£` 内有非 ASCII  
- 国家旗帜 `@TAG` 异常  
- `Concept('key')` 的 key 不是英文  

### 白话解释

`@something!`、`£icon_name£`、概念 key 等是 **资源名**，不是台词。翻成中文后图标消失或报错。

### 怎么做

- 图标名、TAG、Concept key **保持原文**  
- 只翻译周围的说明文字  

---

## 3. 颜色 / 格式标签不成对（显示花屏、一直变色）

### 提示大意

- 颜色标签与结束符数量不匹配  
- 格式标记数量与原文不一致  
- 起始 `#...` / `§...` 与结束 `#!` / `§!` 对不上  

### 白话解释

游戏用特殊标记控制颜色、加粗等，类似「开始染色 → 结束染色」。  
少写结束符时，后面整段都可能一直红/一直粗。

### 例子（示意）

| 游戏习惯（因游戏而异） | 含义 |
|------------------------|------|
| `#R 红色文字#!` | 用 `#` 系格式（常见于 Vic3 等） |
| `§R 红色文字§!` | 用 `§` 系格式（常见于 HOI4 / EU4 / Stellaris 等） |

### 怎么做

1. 数一数：开始标记数量是否等于结束标记  
2. 与 **原文** 对齐：原文有的格式，译文尽量同样保留  
3. 不要只删光所有 `#` / `§` 来「图省事」——可能丢掉游戏需要的结构  

---

## 4. 格式命令后面少了空格

### 提示大意

- 格式化命令 `#xxx` 后面缺少必要空格  
- 例如应写成 `#b 粗体#!`，而不是 `#b粗体#!`

### 白话解释

很多游戏要求：`#标签` 和后面的正文之间有一个空格，否则标签和文字粘在一起，解析失败。

### 怎么做

- 改成：`#标签` + **空格** + 正文 + 结束符  
- 个别特殊标签（视游戏规则）可能例外；以校验提示为准  

---

## 5. 未知格式命令 / 用错游戏的符号

### 提示大意

- 未知的格式化命令 `#bold`  
- Victoria 3 应用 `#`，却检测到 `§`（或其它游戏的符号）  
- 「不支持的格式化命令」

### 白话解释

- 标签名写错了（例如把简写 `#b` 写成了别的）  
- 从另一个游戏的文本 **复制粘贴** 带来了错误符号体系  

### 怎么做

1. 对照 **同游戏原文** 里的写法，不要跨游戏抄格式  
2. Vic3 等以 `#...` / `#!` 为主时，不要留着 HOI4 的 `§...` / `§!`  
3. 不确定的自定义标签：以校验结果为准；Mod 作者自定义标签有时会被规则特殊处理

## 6. 残留源语言标点

### 提示大意

- 检测到残留的源语言标点  
- 列出了本应转换却仍留下的符号  

### 白话解释

译文里还留着原文风格的引号、省略号等，读起来像「中英混排标点」，或不符合中文排版习惯。

### 怎么做

- 按中文习惯替换引号、句读（在不破坏变量与格式标签的前提下）  
- 不要为了改标点而弄坏 `$...$` 或 `#...#!`

## 7. 引号 / 键行结构问题（文件级）

### 可能现象

- 某行 key 缺失、整行解析失败  
- 引号没闭合，后面几十行都乱了  
- 游戏或 Remis 提示文件格式无效  

### 白话解释

P 社本地化行通常类似：

```yml
some_key:0 "这里是文本"
```

少一个 `"`、多删了 key、破坏了缩进，都会让解析器「读崩」。

### 怎么做

1. 用支持高亮的编辑器打开对应 `.yml`  
2. 检查该行是否 **成对双引号**  
3. 不要翻译 **key 本身**（冒号左边）  
4. 保持 UTF-8（游戏侧常见还需 BOM；尽量用 Remis 导出/回写，避免手工另存成错误编码）

## 8. 术语 / 词典相关提示

### 可能现象

- 某术语原文出现多次，译文未按词典统一  
- 同一英文词出现多种中文译法  

### 白话解释

这不一定让游戏崩溃，但会让 Mod 读起来不专业（例如 convoy 有时「船队」有时「护航队」）。

### 怎么做

- 在词典中确认标准译法并统一  
- 对高频词优先人工扫一遍  
- 属于质量问题，不是「格式崩溃」级

## 9. API / 连接 / 程序错误（不是格式校验）

| 你看到的 | 更可能的原因 | 去哪查 |
|----------|--------------|--------|
| Key 无效、401 | Key 填错、过期 | 设置页；[FAQ](faq.md) |
| 429 / 配额 | 额度用尽、频率过高 | 服务商控制台 |
| 超时、连接失败 | 网络、代理、Base URL 错 | [日志](logs-and-diagnostics.md)、Provider 文档 |
| JSON / 模型未按格式返回 | 本地小模型能力不足 | [Ollama 指南](using_ollama.md) |
| 程序闪退 | 看磁盘日志 | [日志与诊断](logs-and-diagnostics.md) |

这些 **不会** 靠「改一句 yml 变量」解决。

---

## 10. 推荐处理顺序（省时间）

1. **先修 ERROR**（变量、方括号指令、图标 key）  
2. 再修 **标签不成对 / 格式标记丢失**  
3. 再处理空格、未知标签、标点  
4. 全部修完后 **重新扫描**，确认问题真正消失  
5. 仍大量误报或程序本身异常 → 带日志去 [GitHub Issues](https://github.com/Drlinglong/Remis/issues)

> 普通客户端 **不能修改 Remis 程序本身**。若你认为某条校验是误报，请在 Issue 里说明游戏、原文、译文与报错原文，方便维护者改进规则。
